# 청킹 전략 비교

RAG 파이프라인 노트에서 청킹을 한 줄로 넘겼는데, 실제로 해 보니 검색 품질에 가장 큰 영향을 주는 단계 중 하나였다. 여러 방식을 비교하고 내 데이터에 맞는 규칙을 정리한다.

## 청크 크기의 트레이드오프

- 너무 크면: 한 청크에 여러 주제가 섞여 임베딩이 흐려진다. 프롬프트에 넣을 수 있는 청크 수도 줄어든다.
- 너무 작으면: 문맥이 잘려 "이것", "위의 방법" 같은 지시어가 무엇을 가리키는지 사라진다. 검색은 됐는데 답을 만들 정보가 부족하다.

정답은 데이터와 질문 유형마다 다르다. 결국 평가 세트로 실험해서 정해야 한다.

## 주요 방식

### 고정 길이 청킹

토큰이나 글자 수로 일정하게 자른다. 구현이 가장 쉽고, 형식이 제각각인 메모에 적합하다.

```python
def fixed_chunks(text, size=500, overlap=50):
    step = size - overlap
    return [text[i:i + size] for i in range(0, len(text), step)]
```

문장 중간이 잘리는 문제가 있어서 문단이나 문장 경계를 우선으로 자르고, 길이 제한을 넘으면 그때 더 자르는 재귀 방식이 많이 쓰인다.

### 오버랩

앞 청크의 끝부분을 다음 청크 앞에 겹쳐 넣는다. 경계에 걸친 정보가 양쪽에 모두 남는다. 대신 저장량이 늘고 검색 결과에 비슷한 청크가 중복으로 올라온다. 10~20% 정도가 흔한 설정이다.

### 구조 기반(제목 계층) 청킹

마크다운 제목(`#`, `##`, `###`)을 기준으로 섹션 단위로 자른다. 스터디 노트처럼 작성자가 이미 의미 단위로 나눠 둔 문서에 잘 맞는다.

```python
# 결과 예시
{"heading_path": ["Postgres 인덱스", "GIN 인덱스", "하이브리드 검색과의 연결"],
 "text": "RAG에서 키워드 검색과 벡터 검색을 섞는..."}
```

섹션이 너무 길면 그 안에서 다시 고정 길이로 나누고, 너무 짧으면 형제 섹션과 합친다.

### 의미 기반 청킹

문장마다 임베딩을 구하고, 인접 문장 간 유사도가 크게 떨어지는 지점에서 자른다. 주제가 바뀌는 곳을 찾는 방식이다. 구조가 없는 일기 같은 글에 시도해 볼 만하지만, 임베딩 호출이 많아 비싸다.

## 제목 경로를 청크에 넣을까

헷갈렸던 점: 제목 경로를 메타데이터로만 저장할지, 임베딩할 텍스트 앞에 붙일지 고민했다. "## 특징" 같은 섹션은 본문만 보면 무엇의 특징인지 알 수 없다. 그래서 임베딩 입력에는 `노트 제목 > 섹션 제목`을 앞에 붙이고, 화면에 보여줄 때는 원문만 보여주는 방식을 택했다. 문맥 없는 청크를 살리는 간단하고 효과적인 방법이라고 생각한다.

## 코드 블록과 표

- 코드 블록 중간에서 자르지 않는다. 마크다운 파서로 블록 경계를 인식해야 한다.
- 표는 행 단위로 자르면 헤더가 사라지므로 통째로 두거나 헤더를 각 조각에 반복한다.

## 실험 계획

같은 평가 질문 세트로 (1) 고정 500자, (2) 제목 계층, (3) 제목 계층 + 제목 경로 접두사를 비교해서 hit rate와 MRR을 기록하려고 한다. 청킹을 바꾸면 전체 재임베딩이 필요하니, 실험 결과는 청킹 버전별로 따로 저장해야 한다.
