# REST API 설계 원칙

지금까지는 백엔드가 만든 API를 받아 쓰는 입장이었는데, 내 프로젝트에서는 직접 엔드포인트를 설계해야 한다. 쓰는 사람 입장에서 불편했던 API를 떠올리며 원칙을 정리했다.

## 리소스 중심으로 URL 짓기

URL은 명사(리소스), 동작은 HTTP 메서드로 표현한다.

```
GET    /notes          노트 목록
POST   /notes          노트 생성
GET    /notes/{id}     노트 하나 조회
PATCH  /notes/{id}     노트 일부 수정
DELETE /notes/{id}     노트 삭제
GET    /notes/{id}/chunks  노트에 속한 청크 목록
```

`/getNotes`, `/deleteNote?id=3` 같은 동사형 URL은 피한다. 복수형을 쓰는 게 일반적이고, 한 프로젝트 안에서는 일관성이 제일 중요하다.

### 동사가 꼭 필요할 때

"재인덱싱 실행"처럼 리소스 CRUD로 표현하기 어려운 동작도 있다. 이럴 땐 `POST /notes/{id}/reindex`처럼 하위 경로에 동작을 두거나, 작업 자체를 리소스로 보고 `POST /jobs`로 만드는 방법이 있다. 후자는 백그라운드 작업 노트에서 다룬 작업 큐 구조와 잘 맞는다.

## 응답 형태의 일관성

### 에러 응답 형식

프론트에서 제일 힘들었던 건 에러 형식이 엔드포인트마다 다른 경우였다. 하나로 통일한다.

```json
{
  "error": {
    "code": "NOTE_NOT_FOUND",
    "message": "노트를 찾을 수 없습니다",
    "details": null
  }
}
```

`code`는 프로그램이 분기하기 위한 값이고, `message`는 사람이 읽기 위한 값이다. 상태 코드와 함께 쓰면 클라이언트가 처리하기 쉽다.

### 페이지네이션

목록 API는 처음부터 페이지네이션을 넣는다. 두 가지 방식이 있다.

- offset 방식: `?limit=20&offset=40`. 구현이 쉽지만 데이터가 중간에 추가되면 항목이 밀리거나 중복된다.
- cursor 방식: `?limit=20&cursor=abc`. 마지막 항목 기준으로 다음을 가져와서 무한 스크롤에 적합하다.

프론트엔드 관점에서 무한 스크롤을 구현할 때 offset 방식 때문에 같은 카드가 두 번 보이는 버그를 겪은 적이 있어서, 이번에는 cursor 방식을 쓰려고 한다.

## 필터, 정렬, 검색

쿼리 파라미터로 표현한다. `GET /notes?source_type=study&sort=-date`. 정렬 필드 앞의 `-`는 내림차순이라는 관례가 있다. 허용하는 필드는 화이트리스트로 제한해야 SQL 주입 위험을 줄일 수 있다.

## 버전 관리

`/v1/notes`처럼 URL에 버전을 넣는 방식이 가장 단순하다. 헤더로 버전을 받는 방식도 있지만, 개인 프로젝트라면 URL 버전이면 충분하다. 중요한 건 기존 클라이언트를 깨뜨리는 변경(필드 삭제, 타입 변경)을 할 때만 버전을 올린다는 원칙이다.

## 상태 코드 선택 요령

- 생성 성공은 201과 `Location` 헤더
- 바디 없는 성공은 204
- 검증 실패는 422(FastAPI 기본값), 형식 자체가 깨졌으면 400
- 중복 생성 충돌은 409

## 느낀 점

REST는 엄격한 표준이라기보다 관례의 모음이다. 완벽한 REST보다 "예측 가능한 API"가 목표라고 생각하기로 했다. OpenAPI 문서를 자동으로 만들어 주는 FastAPI를 쓰면 설계 결과를 바로 눈으로 확인할 수 있어서 좋다.
