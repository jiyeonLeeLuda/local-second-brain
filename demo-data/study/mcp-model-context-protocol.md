# MCP(Model Context Protocol) 개념 정리

도구 호출 노트에서 도구를 JSON Schema로 정의해 모델에 넘기는 법을 배웠다. 그런데 앱마다 도구 정의와 실행 코드를 따로 만들면 같은 기능을 여러 번 구현해야 한다. MCP는 이 연결을 표준화하는 프로토콜이다.

## 한 문장 정의

MCP는 AI 애플리케이션(호스트)이 외부 도구와 데이터 소스(서버)에 연결하는 방법을 정한 공개 프로토콜이다. 흔히 "AI 앱을 위한 USB-C"라고 비유한다. 도구 제공자는 MCP 서버를 한 번 만들면, MCP를 지원하는 여러 클라이언트에서 그대로 쓸 수 있다.

## 구성 요소

### 호스트, 클라이언트, 서버

- 호스트: 사용자가 쓰는 AI 앱(예: 데스크톱 채팅 앱, 코딩 도구, 내가 만들 미니 하네스)
- 클라이언트: 호스트 안에서 서버 하나와 1:1로 연결을 유지하는 부분
- 서버: 도구와 데이터를 제공하는 프로그램(예: 내 노트 검색 서버)

### 서버가 제공하는 것

- Tools: 모델이 호출할 수 있는 함수. 예: `search_notes(query)`
- Resources: 읽을 수 있는 데이터. 파일, 문서 등 URI로 식별된다.
- Prompts: 재사용 가능한 프롬프트 템플릿

헷갈렸던 점: Tools는 모델이 판단해서 호출하는 것이고, Resources는 보통 애플리케이션이나 사용자가 골라서 컨텍스트에 넣는 것이다. 주도권이 누구에게 있는지가 다르다.

## 통신 방식

메시지 형식은 JSON-RPC 2.0이다. 전송 방식은 두 가지가 대표적이다.

- stdio: 호스트가 서버를 자식 프로세스로 실행하고 표준 입출력으로 통신한다. 로컬 도구에 적합하다.
- Streamable HTTP: 원격 서버와 HTTP로 통신한다. 원격 서버는 인증이 필요하며 OAuth 기반 인증이 규정되어 있다. OAuth 노트에서 남겨 둔 궁금증이 여기서 풀렸다.

연결이 시작되면 클라이언트와 서버가 버전과 지원 기능(capabilities)을 주고받는 초기화 단계를 거친 뒤, 클라이언트가 `tools/list`로 도구 목록을 받고 `tools/call`로 호출한다.

## 간단한 서버 예시

Python SDK를 쓰면 데코레이터 하나로 도구를 만들 수 있다.

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("second-brain")

@mcp.tool()
def search_notes(query: str, top_k: int = 5) -> list[dict]:
    """스터디 노트에서 관련 구절을 검색한다."""
    return retriever.search(query, top_k=top_k, source_types=["study"])

if __name__ == "__main__":
    mcp.run()
```

함수의 타입 힌트와 docstring이 그대로 도구 스키마와 설명이 된다. FastAPI가 타입 힌트로 OpenAPI 문서를 만드는 것과 같은 발상이라 익숙했다.

## 보안 관점

MCP 서버는 결국 모델에게 실제 행동 능력을 주는 것이라 경계가 중요하다.

- 서버가 노출하는 도구를 최소화한다. 내 노트 서버는 읽기 전용 검색만 제공한다.
- 개인 일기 같은 민감 소스는 서버 쪽에서 아예 검색 대상에서 빼고, 클라이언트 설정에 맡기지 않는다.
- 신뢰할 수 없는 서버의 도구 설명에 악의적인 지시가 숨어 있을 수 있다(도구 설명도 프롬프트이기 때문). 출처가 확실한 서버만 연결한다.

## 내 프로젝트에서의 위치

계획은 두 방향이다.

1. 우리 앱의 노트 검색을 MCP 서버로 노출해서 다른 AI 도구에서도 내 노트를 검색할 수 있게 한다.
2. 학습용으로 만드는 미니 하네스가 MCP 클라이언트가 되어 그 서버에 연결한다.

양쪽을 다 만들어 보면 프로토콜을 확실히 이해할 수 있을 것 같다.
