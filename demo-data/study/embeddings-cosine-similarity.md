# 임베딩과 벡터 유사도

RAG를 만들려면 "의미가 비슷한 문장을 찾는" 방법부터 이해해야 했다. 그 핵심이 임베딩과 코사인 유사도다. 수학이 약한 편이라 직관 위주로 정리한다.

## 임베딩이란

텍스트를 고정 길이의 숫자 배열(벡터)로 바꾼 것이다. 예를 들어 bge-m3는 문장 하나를 1024개의 실수로 바꾼다.

```python
vec = embed("Postgres 인덱스 정리")
len(vec)  # 1024
```

의미가 비슷한 문장은 벡터 공간에서 가까운 위치에 놓이도록 모델이 학습되어 있다. "강아지"와 "개"는 가깝고, "강아지"와 "트랜잭션"은 멀다. 다국어 모델이라면 "cat"과 "고양이"도 가깝게 놓인다. 영어 문서와 한국어 질문을 연결하려는 계획이 이 성질에 기대고 있다.

### 단어 매칭과의 차이

키워드 검색은 "캐시 무효화"를 검색하면 그 단어가 들어간 문서만 찾는다. 임베딩 검색은 "저장된 값을 언제 지울지"라는 질문으로도 같은 문서를 찾을 수 있다. 반대로 함수 이름이나 에러 코드처럼 정확한 문자열 매칭이 중요한 경우에는 키워드 검색이 더 낫다. 그래서 둘을 섞는 하이브리드 검색이 많이 쓰인다.

## 유사도 측정 방법

### 코사인 유사도

두 벡터 사이 각도의 코사인 값이다. 방향이 같으면 1, 직각이면 0, 반대면 -1.

```python
import numpy as np

def cosine(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))
```

길이(크기)는 무시하고 방향만 본다. 문장 길이에 따라 벡터 크기가 달라지는 영향을 줄여 준다.

### 내적과 유클리드 거리

- 내적(dot product): 방향과 크기를 함께 반영한다.
- 유클리드 거리(L2): 두 점 사이의 직선 거리. 작을수록 가깝다.

헷갈렸던 점: 벡터를 길이 1로 정규화하면 코사인 유사도와 내적이 같아지고, 유클리드 거리 순위도 코사인 순위와 일치한다. 그래서 많은 임베딩 모델이 정규화된 벡터를 내보내고, 어떤 거리 함수를 쓰든 순위가 같다. 다만 정규화 여부는 모델마다 다르니 확인해야 한다.

## 실제로 쓸 때 주의할 점

### 같은 모델로만 비교한다

서로 다른 모델이 만든 벡터는 공간 자체가 달라서 비교가 무의미하다. 모델을 바꾸면 전체를 다시 임베딩해야 한다. Redis 노트에서 캐시 키에 모델 이름을 넣자고 한 이유다.

### 질문과 문서의 비대칭

어떤 모델은 질문용과 문서용 입력에 서로 다른 접두사(`query:`, `passage:` 같은)를 붙이도록 학습되어 있다. 이걸 빼먹으면 성능이 떨어진다. 모델 카드를 확인해야 한다.

### 점수의 절대값은 믿지 않는다

코사인 0.8이 "충분히 비슷하다"인지는 모델마다 다르다. 어떤 모델은 관련 없는 문장끼리도 0.6 이상이 나온다. 절대 임계값보다 순위를 보고, 임계값이 필요하면 내 데이터로 직접 정한다.

## 차원과 저장 공간

1024차원 float32 벡터 하나는 약 4KB다. 청크 10만 개면 약 400MB. 로컬 규모에서는 문제없지만, 검색 속도를 위해 벡터 인덱스가 필요해진다. pgvector와 HNSW 노트로 이어진다.
