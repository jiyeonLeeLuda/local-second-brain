# RAG 파이프라인 전체 그림

내 노트에 질문하면 출처와 함께 답해 주는 기능을 만들려고 한다. 그게 RAG(Retrieval-Augmented Generation)다. 세부 기술은 각각 노트로 나눠 두었고, 여기서는 전체 흐름을 한 장으로 정리한다.

## 왜 RAG인가

LLM은 학습한 시점 이후의 정보나 내 개인 노트를 모른다. 파인튜닝으로 지식을 넣는 방법도 있지만 비싸고, 노트가 바뀔 때마다 다시 학습할 수 없다. RAG는 질문할 때마다 관련 문서를 찾아서 프롬프트에 넣어 주는 방식이다. 모델은 그대로 두고 "열린 책 시험"을 보게 하는 셈이다.

장점은 세 가지다.

- 최신 정보와 개인 데이터를 반영할 수 있다.
- 답의 근거(출처)를 보여줄 수 있다.
- 환각을 줄일 수 있다(완전히 없애지는 못한다).

## 인덱싱 단계 (오프라인)

### 1. 가져오기와 정규화

마크다운 파일을 읽고 frontmatter(날짜, 태그, source_type)를 파싱한다. 파일 해시를 저장해 두면 다음 실행 때 바뀐 파일만 다시 처리할 수 있다.

### 2. 청킹

문서를 검색 단위로 자른다. 너무 길면 관련 없는 내용이 섞이고, 너무 짧으면 맥락이 사라진다. 스터디 노트는 제목 계층 기준으로 자르고 제목 경로를 메타데이터로 남긴다. 자세한 비교는 청킹 전략 노트에 있다.

### 3. 임베딩과 저장

각 청크를 임베딩 모델로 벡터화해서 pgvector 컬럼에 저장한다. 원문, 제목 경로, 파일 경로도 함께 저장해야 나중에 출처를 보여줄 수 있다.

## 질의 단계 (온라인)

### 4. 검색

질문을 같은 임베딩 모델로 벡터화하고, 가까운 청크 top-k를 찾는다. 키워드 검색 결과와 합치는 하이브리드 검색이나, 소스 타입 필터를 여기서 적용한다.

### 5. 재정렬 (선택)

검색된 후보를 리랭커 모델로 다시 점수 매겨 순서를 바꾼다. 임베딩 검색은 빠르지만 거칠고, 리랭커는 느리지만 정밀하다. 후보 20~50개를 리랭킹해서 상위 5개만 쓰는 식이다.

### 6. 프롬프트 구성과 생성

```text
다음 자료만 근거로 답하세요. 근거가 없으면 모른다고 답하세요.
각 문장 끝에 [출처 번호]를 붙이세요.

[1] postgres-indexes.md > B-tree 인덱스
...
[2] pgvector-hnsw-ivfflat.md > HNSW
...

질문: 벡터 검색에 왜 B-tree를 못 쓰나요?
```

프롬프트 작성 원칙은 프롬프트 엔지니어링 노트에 따로 정리했다.

### 7. 출처 표시

답과 함께 사용된 청크의 파일명과 제목 경로를 보여준다. 사용자가 원문을 바로 열어 확인할 수 있어야 신뢰가 생긴다.

## 어디서 실패하는가

헷갈렸던 점: 답이 이상할 때 LLM 탓을 먼저 했는데, 실제로는 검색 단계에서 이미 잘못된 청크를 가져온 경우가 훨씬 많았다. 그래서 문제를 단계별로 나눠 봐야 한다.

- 검색 실패: 정답 청크가 top-k에 없다. 청킹, 임베딩 모델, 질문 표현을 의심한다.
- 생성 실패: 정답 청크가 있는데도 답이 틀리거나 근거를 무시한다. 프롬프트, 모델 크기, 컨텍스트 길이를 의심한다.

검색 단계는 hit rate나 MRR로 따로 측정할 수 있다. RAG 평가 노트에 정리했다.

## 에이전트형 RAG와의 차이

위 흐름은 질문 한 번에 검색 한 번인 고정 파이프라인이다. 에이전트형은 LLM이 검색 도구를 직접 호출하며 필요하면 여러 번 검색한다. 유연하지만 느리고 예측하기 어렵다. 도구 호출 노트에서 이어서 다룬다. 우선은 고정 파이프라인으로 기준선을 만든다.
