# 메시지 큐와 백그라운드 작업

노트 수백 개를 한꺼번에 임베딩하는 작업을 HTTP 요청 안에서 처리하면 요청이 몇 분씩 걸리고 타임아웃이 난다. 이런 일은 요청과 분리해서 뒤에서 처리해야 한다. 그 구조를 공부했다.

## 왜 요청 밖으로 빼야 하나

- 사용자는 기다리지 않고 "작업 접수됨" 응답을 바로 받는다.
- 오래 걸리는 작업이 웹 서버 워커를 붙잡지 않는다.
- 실패하면 재시도할 수 있다.
- 작업량이 몰려도 큐에 쌓아 두고 천천히 처리한다(버퍼 역할).

프론트엔드 관점에서 보면 "파일 업로드 후 처리 중 스피너, 완료되면 알림" UX의 뒤편이 이 구조다.

## 기본 구성 요소

### 프로듀서, 큐, 컨슈머

- 프로듀서: 작업을 큐에 넣는 쪽(API 서버)
- 큐(브로커): 작업을 보관하는 곳(Redis, RabbitMQ, 또는 Postgres 테이블)
- 컨슈머(워커): 큐에서 작업을 꺼내 실행하는 별도 프로세스

### 작업 상태를 API로 노출하기

```
POST /jobs           -> 202 Accepted, {"job_id": "j-123"}
GET  /jobs/j-123     -> {"status": "running", "progress": 0.4}
```

REST 설계 노트에서 말한 "작업 자체를 리소스로 보기"가 이것이다. 클라이언트는 폴링하거나 SSE로 진행 상황을 받는다.

## 전달 보장과 멱등성

### at-least-once

대부분의 큐는 "최소 한 번 전달"을 보장한다. 워커가 작업을 처리하다 죽으면 같은 작업이 다른 워커에게 다시 간다. 즉 **같은 작업이 두 번 실행될 수 있다.**

그래서 작업은 멱등하게 만들어야 한다. 예를 들어 "노트 42를 재인덱싱"은 기존 청크를 지우고 다시 넣으니 두 번 실행해도 결과가 같다. 반면 "카운트 +1" 같은 작업은 두 번 실행되면 틀린다.

헷갈렸던 점: exactly-once는 대부분 시스템에서 사실상 불가능하거나 비싸다. 현실적인 해법은 at-least-once + 멱등한 작업이다. HTTP 노트의 멱등성 개념이 여기서 다시 나왔다.

### 재시도와 데드 레터 큐

- 재시도 간격은 지수 백오프(1초, 2초, 4초...)로 늘린다.
- 계속 실패하는 작업은 데드 레터 큐로 옮겨 사람이 확인하게 한다. 무한 재시도는 큐를 막는다.

## Python에서의 선택지

- Celery: 오래되고 기능이 많지만 설정이 복잡하다.
- RQ, Dramatiq, arq: 더 가볍다. arq는 asyncio 기반이다.
- Postgres를 큐로 쓰기: `SELECT ... FOR UPDATE SKIP LOCKED`로 여러 워커가 서로 다른 행을 가져가게 할 수 있다.

```sql
SELECT id FROM jobs
WHERE status = 'queued'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED`는 다른 워커가 잠근 행을 건너뛴다. 트랜잭션 노트의 행 잠금 개념을 응용한 방식이다. 이미 Postgres를 쓰고 있으니 인프라를 늘리지 않아도 된다는 게 큰 장점이다.

## FastAPI BackgroundTasks는 큐가 아니다

FastAPI의 `BackgroundTasks`는 응답을 보낸 뒤 같은 프로세스에서 함수를 실행해 줄 뿐이다. 서버가 재시작되면 작업이 사라지고, 재시도도 없다. 이메일 한 통 보내기 정도에는 괜찮지만 대량 임베딩 같은 작업에는 맞지 않는다.

## 내 프로젝트 계획

노트 내 조사 작업과 재인덱싱은 Postgres 기반 작업 테이블 + 별도 워커 컨테이너로 시작한다. docker compose에 `worker` 서비스를 추가하고, 동시 실행 수는 로컬 LLM 서버가 버틸 수 있는 수준으로 제한한다.
