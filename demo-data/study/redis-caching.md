# Redis와 애플리케이션 캐싱

HTTP 캐싱 노트가 브라우저와 CDN 쪽 이야기였다면, 이번에는 서버 안에서 쓰는 캐시다. 로컬 LLM 호출과 임베딩 계산이 느리기 때문에 같은 입력에 대한 결과를 저장해 두면 효과가 클 것 같아서 공부했다.

## Redis란

메모리 기반 키-값 저장소다. 디스크 기반 DB보다 훨씬 빠르고, 단순 문자열 외에도 해시, 리스트, 셋, 정렬된 셋 같은 자료구조를 지원한다. 캐시, 세션 저장소, 작업 큐, 속도 제한 등에 두루 쓰인다.

```bash
SET embed:3f9a "[0.12, -0.03, ...]" EX 86400
GET embed:3f9a
TTL embed:3f9a
```

`EX`로 만료 시간을 초 단위로 준다.

## 캐싱 패턴

### Cache-Aside (Lazy Loading)

가장 흔한 패턴이다.

1. 캐시에서 먼저 찾는다.
2. 있으면(hit) 그대로 반환한다.
3. 없으면(miss) DB나 원본에서 계산하고, 결과를 캐시에 넣은 뒤 반환한다.

```python
def get_embedding(text: str):
    key = "embed:" + sha256(text.encode()).hexdigest()
    cached = r.get(key)
    if cached:
        return json.loads(cached)
    vec = call_embedding_api(text)
    r.set(key, json.dumps(vec), ex=86400)
    return vec
```

입력 텍스트의 해시를 키로 쓰면 같은 문장을 다시 임베딩하지 않는다. 프로젝트의 "재실행 시 변경분만 처리" 목표와도 맞닿아 있다. 다만 이건 DB에 `content_hash`를 저장하는 방식으로도 해결되니 Redis가 꼭 필요한지는 더 따져 봐야 한다.

### Write-Through

DB에 쓸 때 캐시도 같이 갱신한다. 읽기 일관성이 좋지만 쓰기가 느려진다.

## 캐시 무효화

"컴퓨터 과학에서 어려운 두 가지는 캐시 무효화와 이름 짓기"라는 말이 괜히 있는 게 아니었다.

- TTL로 시간이 지나면 자연스럽게 만료시킨다.
- 데이터가 바뀌면 관련 키를 직접 삭제한다.
- 키에 버전을 넣는다. 예: 임베딩 모델을 바꾸면 `embed:v2:...`로 키 접두사를 바꿔서 이전 캐시를 통째로 무시.

헷갈렸던 점: 모델이 바뀌었는데 캐시된 임베딩을 계속 쓰면, 서로 다른 벡터 공간의 값이 섞여 검색 결과가 엉망이 된다. 모델 이름을 캐시 키에 넣는 게 안전하다.

## 캐시 스탬피드

인기 있는 키가 만료되는 순간 많은 요청이 동시에 miss를 내고, 모두 원본을 계산하러 몰리는 현상이다. LLM처럼 계산이 비싼 경우 치명적이다.

- 한 요청만 계산하도록 잠금을 건다(`SET key value NX EX 10`).
- 만료 시간에 약간의 무작위 값을 더해 동시에 만료되지 않게 한다.

## 메모리 정책

Redis는 메모리가 꽉 차면 `maxmemory-policy`에 따라 키를 버린다. 캐시 용도라면 `allkeys-lru`가 무난하다. 반대로 작업 큐 용도로 같은 Redis를 쓴다면 큐 데이터가 버려지면 안 되므로 인스턴스를 분리하거나 정책을 신중히 정해야 한다.

## 정리

캐시는 "빨라지는 대신 틀릴 수 있는" 선택이다. 무엇을, 얼마나 오래, 어떻게 지울지를 먼저 정하고 넣어야 한다. 개인 프로젝트 첫 단계에서는 DB의 해시 비교로 충분하고, LLM 응답 캐시가 필요해지면 그때 Redis를 도입하기로 했다.
