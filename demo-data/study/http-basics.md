# HTTP 기초와 메서드 정리

프론트엔드에서 `fetch`만 쓰다 보니 HTTP를 "요청 보내면 JSON 오는 것" 정도로만 이해하고 있었다. 백엔드를 공부하면서 서버 입장에서 요청을 받아 보니 생각보다 약속이 많다는 걸 알게 되어 처음부터 다시 정리한다.

## 요청과 응답의 구조

HTTP는 텍스트 기반의 요청/응답 프로토콜이다. 클라이언트가 요청을 보내면 서버가 정확히 하나의 응답을 돌려준다. 요청은 크게 세 부분으로 나뉜다.

- 시작 줄: 메서드, 경로, 버전 (`GET /notes/3 HTTP/1.1`)
- 헤더: `Host`, `Content-Type`, `Authorization` 같은 메타데이터
- 바디: POST나 PUT에서 보내는 실제 데이터

응답도 비슷하게 상태 줄, 헤더, 바디로 되어 있다. 브라우저 개발자 도구의 Network 탭에서 매일 보던 화면이 사실 이 구조를 표로 보여준 것뿐이었다.

```http
POST /api/notes HTTP/1.1
Host: localhost:8000
Content-Type: application/json

{"title": "HTTP 공부", "body": "..."}
```

## 메서드별 의미

### GET, POST, PUT, PATCH, DELETE

- `GET`: 리소스를 조회한다. 서버 상태를 바꾸면 안 된다.
- `POST`: 새 리소스를 만들거나, 딱 맞는 메서드가 없는 처리를 요청한다.
- `PUT`: 리소스 전체를 주어진 내용으로 교체한다.
- `PATCH`: 리소스 일부만 수정한다.
- `DELETE`: 리소스를 삭제한다.

헷갈렸던 점은 PUT과 PATCH의 차이였다. PUT은 "이 모양으로 통째로 바꿔줘"라서 빠진 필드는 비워지는 것이 원칙이고, PATCH는 보낸 필드만 바뀐다. 실제로는 PUT을 PATCH처럼 구현하는 서버도 많아서 API 문서를 꼭 확인해야 한다.

### 안전한 메서드와 멱등성

"안전(safe)"은 서버 상태를 바꾸지 않는다는 뜻이고, "멱등(idempotent)"은 같은 요청을 여러 번 보내도 결과 상태가 한 번 보낸 것과 같다는 뜻이다.

| 메서드 | 안전 | 멱등 |
|---|---|---|
| GET | O | O |
| PUT | X | O |
| DELETE | X | O |
| POST | X | X |
| PATCH | X | 보장 안 됨 |

멱등성이 왜 중요한지는 재시도를 생각하면 바로 이해된다. 네트워크가 끊겨서 응답을 못 받았을 때 PUT은 다시 보내도 안전하지만, POST는 주문이 두 번 생길 수 있다. 그래서 결제 API에서 `Idempotency-Key` 헤더를 받는 경우가 있다.

## 상태 코드

상태 코드는 첫 자리만 기억해도 대부분 해결된다.

- 2xx 성공: 200 OK, 201 Created, 204 No Content
- 3xx 리다이렉트: 301, 302, 304 Not Modified(캐시 노트에서 다시 나온다)
- 4xx 클라이언트 잘못: 400, 401, 403, 404, 409, 422
- 5xx 서버 잘못: 500, 502, 503

### 401과 403의 차이

401은 "너 누군지 모르겠다(인증 안 됨)", 403은 "누군지는 아는데 권한이 없다"이다. 로그인 만료 시 프론트에서 401을 받으면 토큰 갱신을 시도하고, 403이면 권한 안내 화면을 보여주는 식으로 분기했던 기억이 난다. 이름이 Unauthorized라서 더 헷갈린다.

## 프론트엔드 관점에서 느낀 점

`fetch`는 4xx, 5xx 응답에서도 reject되지 않는다. `response.ok`를 확인하지 않으면 에러를 성공처럼 처리하게 된다. 서버를 직접 만들어 보니 상태 코드를 정확히 돌려주는 게 클라이언트 개발자에 대한 배려라는 걸 느꼈다. 앞으로 FastAPI에서 엔드포인트를 만들 때 201과 204를 제대로 구분해서 쓰기로 했다.
