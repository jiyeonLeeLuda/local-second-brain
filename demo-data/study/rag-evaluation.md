# RAG 검색 평가: hit rate와 MRR

청킹 방식이나 임베딩 모델을 바꿨을 때 "더 좋아졌다"를 느낌이 아니라 숫자로 말하고 싶었다. RAG 파이프라인 노트에서 말했듯 실패의 대부분은 검색 단계에서 생기니, 검색부터 따로 평가한다.

## 평가 세트 만들기

질문과 "정답 위치"의 쌍을 만든다.

```yaml
- id: q01
  question: "배열 컬럼에서 특정 원소를 포함하는 행을 빠르게 찾으려면?"
  expected_file: postgres-indexes.md
  expected_heading: GIN
```

### 좋은 평가 질문의 조건

- 정답이 한 섹션에 분명히 있다.
- 섹션 문장을 그대로 베끼지 않고 다른 표현으로 묻는다. 그대로 베끼면 키워드 일치만으로 맞혀서 점수가 부풀려진다.
- 여러 노트에 걸친 주제(예: 멱등성은 HTTP 노트와 큐 노트 모두에 나옴)도 일부 넣어 헷갈리는 상황을 만든다.
- 다른 언어로 묻는 질문을 섞어 다국어 검색을 확인한다.

헷갈렸던 점: 처음에 내가 노트를 쓴 직후에 질문을 만들었더니 노트 문장을 거의 그대로 썼다. 며칠 지나 기억이 흐려진 뒤에 만드는 게 실제 사용 상황에 가깝다.

## 지표

### Hit Rate (Recall@k)

정답 청크가 상위 k개 안에 하나라도 들어 있는 질문의 비율이다.

```python
def hit_rate(results, k=5):
    hits = sum(1 for r in results if r.expected in r.retrieved[:k])
    return hits / len(results)
```

이해하기 쉽고, "LLM에게 넘기는 k개 안에 정답이 있는가"를 바로 보여준다. 단점은 정답이 1등이든 5등이든 똑같이 취급한다는 것.

### MRR (Mean Reciprocal Rank)

정답이 처음 나타난 순위의 역수를 평균 낸 값이다. 1등이면 1, 2등이면 0.5, 3등이면 0.33, 못 찾으면 0.

```python
def mrr(results):
    total = 0.0
    for r in results:
        for rank, item in enumerate(r.retrieved, start=1):
            if item == r.expected:
                total += 1 / rank
                break
    return total / len(results)
```

순위가 높을수록 보상이 커서, 정답을 위로 끌어올리는 개선(예: 리랭커)을 잘 반영한다.

### nDCG

정답이 여러 개이고 관련도에 등급이 있을 때 쓴다. 지금 평가 세트는 정답이 하나라 hit rate와 MRR로 충분하다.

## 정답 판정 기준

청크 ID로 비교하면 청킹 방식을 바꿀 때마다 정답이 무효가 된다. 그래서 정답을 "파일명 + 제목 일부"로 정의하고, 검색된 청크의 `heading_path`에 그 제목이 포함되면 정답으로 본다. 청킹 실험 간 공정한 비교를 위한 장치다.

## 생성 단계 평가

검색이 맞아도 답이 틀릴 수 있다. 생성 평가는 더 어렵다.

- 충실성(faithfulness): 답이 근거 자료에 있는 내용만 말하는가
- 답변 관련성: 질문에 실제로 답했는가
- 출처 정확성: 단 출처 번호가 실제 근거와 맞는가

LLM을 채점자로 쓰는 방법(LLM-as-a-judge)이 있지만, 작은 로컬 모델은 채점이 불안정하다. 처음에는 10~20개를 직접 읽고 표로 기록하는 게 현실적이다.

## 기록 방식

실험할 때마다 설정(청킹 버전, 임베딩 모델, k, 리랭커 여부)과 결과 지표를 한 줄씩 남긴다. 질문별 순위도 저장하면 어떤 질문이 계속 실패하는지 볼 수 있다. 평균 숫자보다 실패 사례를 들여다볼 때 개선 아이디어가 더 많이 나왔다.
