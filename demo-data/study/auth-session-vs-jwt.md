# 인증: 세션 방식과 JWT 비교

프론트엔드에서 로그인 기능을 붙일 때 "토큰을 localStorage에 넣을까, 쿠키에 넣을까"로 팀에서 길게 논쟁한 적이 있다. 그때는 결론만 따랐는데, 백엔드 입장에서 두 방식을 비교해 보니 각자 이유가 있었다.

## 세션 기반 인증

### 동작 흐름

1. 사용자가 아이디와 비밀번호로 로그인한다.
2. 서버가 세션 ID를 만들고, 서버 쪽 저장소(메모리, Redis, DB)에 사용자 정보를 저장한다.
3. 세션 ID를 `Set-Cookie`로 내려준다.
4. 이후 요청마다 브라우저가 쿠키를 자동으로 보내고, 서버는 저장소에서 세션을 찾는다.

### 장점과 단점

- 장점: 서버가 상태를 쥐고 있어서 강제 로그아웃이 쉽다. 세션을 지우면 끝.
- 단점: 서버가 여러 대면 세션 저장소를 공유해야 한다. 그래서 Redis를 세션 저장소로 많이 쓴다.

## JWT 기반 인증

### 토큰 구조

JWT는 `header.payload.signature` 세 부분을 점으로 이은 문자열이다. payload에는 `sub`(사용자 ID), `exp`(만료 시각) 같은 클레임이 들어간다.

```python
import jwt
token = jwt.encode({"sub": "user-1", "exp": 1767225600}, SECRET, algorithm="HS256")
claims = jwt.decode(token, SECRET, algorithms=["HS256"])
```

헷갈렸던 점: payload는 암호화가 아니라 Base64URL 인코딩일 뿐이라 누구나 읽을 수 있다. 서명은 "위조되지 않았다"는 것만 보장한다. 그러니 비밀번호나 민감 정보를 payload에 넣으면 안 된다.

### 장점과 단점

- 장점: 서버가 저장소를 조회하지 않고 서명만 검증하면 된다(stateless). 여러 서비스가 같은 키로 검증할 수 있다.
- 단점: 발급한 토큰을 중간에 무효화하기 어렵다. 만료 전까지는 유효하다.

## 액세스 토큰과 리프레시 토큰

JWT의 무효화 문제를 줄이려고 두 종류를 쓴다.

- 액세스 토큰: 수명이 짧다(예: 15분). API 호출에 쓴다.
- 리프레시 토큰: 수명이 길다. 새 액세스 토큰을 받을 때만 쓴다. 서버에 저장해 두고 폐기할 수 있게 하는 경우가 많다.

결국 리프레시 토큰을 서버에 저장하면 어느 정도는 다시 stateful해진다. "JWT는 무조건 stateless"라는 말은 반쯤만 맞다.

## 토큰을 어디에 저장할까

### localStorage vs HttpOnly 쿠키

- localStorage: JS로 읽을 수 있어서 XSS가 발생하면 토큰이 탈취된다.
- HttpOnly 쿠키: JS에서 읽을 수 없어서 XSS에 상대적으로 강하다. 대신 CSRF를 막기 위해 `SameSite=Lax` 이상과 필요 시 CSRF 토큰을 함께 쓴다.

프론트엔드 관점에서 보면 쿠키 방식은 CORS 설정과 `credentials: "include"`를 맞춰야 해서 처음엔 귀찮지만, 보안상 더 낫다는 쪽으로 정리했다. CORS 노트에 자격 증명 관련 내용을 이어서 적었다.

## 내 프로젝트에서의 선택

로컬에서 혼자 쓰는 노트 앱은 Tailscale 망 안에서만 접근하니 복잡한 인증이 당장 필요하지 않다. 그래도 나중을 위해 단순한 세션 쿠키 방식으로 시작하고, 외부 클라이언트(MCP 서버 등)가 붙을 때 토큰 방식을 검토하려고 한다. 소셜 로그인은 OAuth 노트에서 따로 다룬다.
